# Refuse commands that use unset variables

Slug: k-setup-command-references-unset-variable
Model: not applicable — this adds a stateless lexical Validate rule and one InitContext input; the existing bounded correction conversation is unchanged
Acceptance:
- .kogen/intents/k-setup-command-references-unset-variable/acceptance.feature
- features/steps/k-setup-command-references-unset-variable__validate.js

Init verifies each proposed setup, check and fix command by running it in the environment of the person running init (the session environment plus the `KOGEN_NODE`, `KOGEN_QUINT` and `KOGEN_CUCUMBER` variables initExec adds). Today a command that expands a variable that is not set there (`go test $PKGS`, `cd "$APP_DIR" && make test`, `pytest $TEST_ARGS`) silently expands to an empty string, can pass vacuously or run something else, and is written to the configuration; nothing in Validate mentions the dependency. After this change, setup/init.go Validate refuses a proposed setup, fix or check command that references a variable which is not set in the init environment, is not assigned earlier in the same command, is not one of the shell's own, and has no default form. The problem names the variable and tells the model to use a literal value or a project path instead. As with every Validate problem, the problems go back to the model through the existing single correction; a second invalid answer ends init with provider/init_invalid (exit 4) and nothing is written. Commands without variable references and all other validation, merging, verification, summary output, the init prompt (`setup/prompts/init.md`), the `submit_configuration` tool definition and the golden files are unchanged. Commands are not executed to detect references.

## Decisions
- Interface: `setup.InitContext` gains a field `Env []string`: the environment the verification commands run in, as `NAME=value` entries (the form of `sys.Session.Env`). initAsk sets it to a copy of `s.Env` followed by `KOGEN_NODE=<path>`, `KOGEN_QUINT=<path>` and `KOGEN_CUCUMBER=<path>` for each non-empty value of `in.Tools` (exactly the variables initExec adds), and the value is always non-nil, even for an empty session environment. The same InitContext reaches both the provider route (initConverse) and the external route (initClaudeConverse). (source: request)
- A nil `Env` means the environment is not known, and Validate does not apply the unset-variable rule, so that existing validation tests stay green. Existing callers that pass `InitContext{}` (such as TestValidateCredentials with `$NPM_TOKEN` and `${API_KEY}`, and the committed k-setup-refuse-secret-literals acceptance) keep their current results unchanged. A name counts as set when any `Env` entry's text before its first `=` equals the name, whatever the value, including an empty one. (source: request)
- References are found lexically, left to right, over the whole command text. Text between single quotes outside double quotes is not scanned. Inside double quotes, scanning continues and `'` is an ordinary character. Outside single quotes, a backslash escapes the next character, so `\$NAME` is not a reference. A reference is `$NAME` (NAME is the longest match of `[A-Za-z_][A-Za-z0-9_]*`) or `${NAME` followed by `}` or any other character. `$(`, `$((` and a `$` that is not followed by a name, a brace or a special character are not variable references; text inside command substitutions is scanned like the rest of the command. (source: request)
- Never refused: special and positional parameters (`$?`, `$#`, `$$`, `$!`, `$-`, `$@`, `$*`, `$0`–`$9` and their braced forms), and the shell's own names `HOME`, `PWD`, `PATH` and `USER`. The existing outside-project rule still refuses `$HOME`/`${HOME}` exactly as today. (source: request)
- Default forms are never refused: `${NAME:-x}`, `${NAME-x}`, `${NAME:=x}` and `${NAME=x}`. (source: request)
- "Assigned earlier in the same command": before the reference's position, outside single quotes, the command contains either a word that begins `NAME=` (this covers `NAME=value cmd`, a standalone `NAME=value;` and `export NAME=...`), or the word `for` followed by the word `NAME`. A word starts at the beginning of the command or after whitespace or one of `;`, `&`, `|`, `(`, `)` or a newline. An assignment that appears only after the reference does not count (`echo $X; X=1` is refused). (source: request)
- Problem wording, one problem per distinct refused name, in the order of each name's first refused reference: `check <name> (<command>) references variable <NAME>, which is not set in the init environment; use a literal value or a project path instead`, `setup command <command> references variable <NAME>, which is not set in the init environment; use a literal value or a project path instead`, and `fix command <command> references variable <NAME>, which is not set in the init environment; use a literal value or a project path instead`. (source: request)
- Placement: the rule applies to proposed setup, fix and check commands only (detected checks are not re-validated, as today). Its problems are appended after that command's existing problems: after the publishes-or-deploys problem for setup and fix commands, and after the runs-nothing/ignores-its-own-failure problem for checks. Commands that existing validation already skips with `continue` (a credential literal, or a control character) get no unset-variable problem. As with any problem, Validate returns an empty InitProposal. (source: request)
- Keep the one correction opportunity: an invalid proposal goes back once as `invalid: <problems joined by "; ">`, and a second invalid proposal stops with provider/init_invalid exit 4 and nothing written. No new retries. (source: request)

## Source comparison
- Addressed: Problem/Need map to the Validate rule, the InitContext.Env interface fed from the initExec environment, and the exact wording above. Every Synthetic acceptance example is a literal executable row in acceptance.feature, run with `InitContext.Env` = `["SET_ONE=1"]` and UNSET_ONE not set: `echo $SET_ONE` accepted; `echo $UNSET_ONE` refused naming UNSET_ONE; `UNSET_ONE=x sh -c 'true'`, `export UNSET_ONE=x; echo "$UNSET_ONE"` and `echo ${UNSET_ONE:-fallback}` accepted; `echo '$UNSET_ONE'` accepted and `echo "$UNSET_ONE"` refused; setup `cd "${UNSET_ONE}" && make` and fix `fmt $UNSET_ONE` refused with the same wording.
- Conflicting, resolved: the request lists `echo $HOME $PWD $?` as accepted, but the existing outside-project rule (k-setup-command-leaves-project-folder) refuses `$HOME` with `check t (echo $HOME $PWD $?) reaches outside the project folder; use a path inside the project`, and the request also says all other validation is unchanged. The unchanged-validation sentence wins: that command gets no unset-variable problem and keeps only its existing outside-project problem (exact acceptance row). A separate row, `echo $PWD $PATH $USER $? $1 $# $@ $* $$ $! $- $0`, shows the shell's own and special parameters fully accepted.
- Added boundary rows from the Need wording: `for UNSET_ONE in`, `${UNSET_ONE-x}`/`${UNSET_ONE:=y}`, `${SET_ONE}`, an assignment that comes after the reference (refused), two unset names (two problems, in order, each named once), and commands without references (`go test ./...`, `npm ci`, `gofmt -w .`) accepted.
- Added end-to-end Init scenarios through `setup.Init` with a loopback model: a check that uses SET_ONE (set in the caller environment) and KOGEN_NODE (given only through InitInput.Tools) is kept, and a check that uses UNSET_ONE is corrected once, then init ends with exit 4 and no configuration. This guards the wiring of Env into InitContext, which nil-Env Validate tests alone would miss.
- "Existing validation tests stay green": unchanged tests TestValidateCredentials, TestValidateCommandsOutsideProject, TestInitVerifyBudgetStopsRemainingCommands (`$RUN_LOG` set in the session environment), TestInitRunsFixersOnceAfterTheChecksOnTheCopy (`$KOGEN_NODE` from the tools), TestInitFailedFixerOutputBoundaries (`i=1; ... "$i"`) and TestInitMutationPathListAtFive (`for p in ...; "$p"`) run in acceptance; the configured go-test check runs the rest.
- Background only, not a new requirement: the request notes that nothing in the summary mentions the dependency. Need only asks for refusal at Validate, so the summary output is unchanged.

## Tests
- Refuse an unset `$NAME`/`${NAME}` reference in proposed setup, fix and check commands, with the exact problem per role, one per distinct name in first-reference order, and an empty proposal: add a focused Validate table test with `InitContext{Env: []string{"SET_ONE=1"}}` (unit)
- Accept references that are set in Env, assigned earlier (`NAME=value cmd`, `export NAME=`, `for NAME in`), default forms, single-quoted text, and shell's own/special/positional parameters; refuse a double-quoted reference and one assigned only later; keep the existing `$HOME` outside-project problem as the only problem for `echo $HOME $PWD $?`: same table (unit)
- Init passes the verification environment (session env plus non-empty KOGEN_* tool variables) into Validate, and a refused command is corrected once and then ends with provider/init_invalid, nothing written: add an Init test with the initNewFx fixture, one case proposing a check using a variable set in `f.env`, one proposing a check using an unset variable twice (integration)
- A nil Env leaves Validate unchanged, and all other validation and init behavior is unchanged: existing TestValidateCredentials, TestValidateCommandsOutsideProject, Init tests and the configured go-test check (existing)
