# Report Claude route usage in init progress line

Slug: k-setup-init-claude-route-usage-reported
Model: not applicable — a per-run sum over at most two shaping rounds with an unknown flag; no persistent state or interacting rules
Acceptance:
- .kogen/intents/k-setup-init-claude-route-usage-reported/acceptance.feature
- features/steps/k-setup-init-claude-route-usage-reported__usage.js

`kogen init` prints one progress line to stderr (`s.Progress`) after the shaping model answers, in `initAsk` in `setup/init.go`: `kogen: init <model>/<effort> input=N cached=N output=N reasoning=N wall_ms=N` (the counters are `provider.Usage.Line()`). On the Claude Code route (`role.External()`), the conversation runs through `initClaudeConverse` in `setup/init_route.go`, which discards every round's `executor.RoundResult.Usage`. As a result the line always reads `input=0 cached=0 output=0 reasoning=0`. Observed on the unchanged tree with the acceptance fixture: `kogen: init claude-sonnet-5-5/high input=0 cached=0 output=0 reasoning=0 wall_ms=111` after two rounds that reported usage. When the model never returns a valid configuration (`provider/init_invalid`, exit 4), `initAsk` returns the error before printing, so the line is missing on both routes. Observed on the unchanged tree: stderr goes from `kogen: asking ... about the project's commands` directly to `provider/init_invalid: the model did not return a valid configuration; nothing was written`.

The product should behave as follows.

1. **Claude Code route sum.** `initClaudeConverse` also returns the usage of the rounds that ran (one, or two when the first answer was missing or invalid). The usage is the sum of each round's `executor.RoundResult.Usage` (package `github.com/KogenAI/kogen-executor/executor`). A round's usage is usable when its `Input`, `Cached` and `Output` are all reported (non-nil). For the claudecode adapter this is the state `complete`. `Input` is the executor's own figure: input_tokens + cache_read_input_tokens + cache_creation_input_tokens. It is used as reported and is not recomputed. Claude Code does not report reasoning, so a nil `Reasoning` counts as 0. A reported `Reasoning` is added. The sum is printed with the existing `provider.Usage.Line()` format, so the line reads `kogen: init <model>/<effort> input=I cached=C output=O reasoning=R wall_ms=W`. Example: one round reporting Input 100, Cached 40, Output 10 gives `kogen: init claude-sonnet-5-5/high input=100 cached=40 output=10 reasoning=0 wall_ms=W`. An invalid first round reporting 100/40/10 plus a valid second round reporting 50/50/5 gives `input=150 cached=90 output=15 reasoning=0`.
2. **Unknown usage.** If any round that ran on the Claude Code route has no usable usage (no usage reported, or only some of Input/Cached/Output), the line is `kogen: init <model>/<effort> usage=unknown wall_ms=W`. `usage=unknown` replaces the four counters, and no zero counters are printed. This happens even when the other round reported usage. Example: an invalid first round reporting 100/40/10 followed by a valid round without usage gives `usage=unknown`.
3. **Line printed on init_invalid.** If the conversation ends with `provider/init_invalid` on either route, `initAsk` prints the usage line first. On the Claude Code route the line follows rules 1–2. On the direct route it is the `provider.Usage` sum that `initConverse` already returns with the error. `initAsk` then returns the same error unchanged: same class, reason and detail, exit 4. Nothing is written. With `cmd/kogen-setup`, stderr therefore ends with the usage line followed by `provider/init_invalid: the model did not return a valid configuration; nothing was written`. Its stdout JSON keeps `exit` 4 and `configuration` null. Example on the direct route: two invalid answers reporting 100/0/20/5 and 30/10/6/2 print `kogen: init gpt-6.1-sol/high input=130 cached=10 output=26 reasoning=7 wall_ms=W` before the error.
4. **Unchanged.** The following do not change:
   - The direct provider route's successful line, byte for byte except the measured `wall_ms` (for example `kogen: init gpt-6.1-sol/high input=100 cached=0 output=20 reasoning=5 wall_ms=W`), and its sum over both attempts.
   - The `wall_ms` field: milliseconds since the `kogen: asking ...` line.
   - The position of the line, right after the conversation and before `kogen: checking the acceptance runner`.
   - Every other progress or stdout line, and the exit codes.
   - Other failures: a provider request error, an executor start or round failure, or an interrupt. These still return without printing the usage line, as today.

The following do not change either: the prompt and tool definitions, the requests sent, the feedback given to the second round, the configuration written, the commit, and the contract suite. No setting or option is added.

The acceptance step builds `cmd/kogen-setup` from the checkout (`go build -o <tmp>/kogen-setup ./cmd/kogen-setup`) and runs it on a synthetic repository. It reads Init's progress lines and error from the command's stderr and its JSON result from stdout, as documented in README.md. On the Claude Code route it installs a scripted Claude Code runtime at `$HOME/.kogen/claude-code/2.1.312/claude`, modelled on `features/steps/provider-init.js`, which answers each invocation (round 1 `--session-id`, round 2 `--resume`) with a `result` line whose `structured_output` is the scripted answer and whose `usage` is the scripted usage. On the direct route it uses a scripted Responses-API server on `KOGEN_PROVIDER_URL` with a saved ChatGPT login, modelled on `initSubmit`/`initUsage` in `setup/init_test.go`. The valid answer is `{"setup":[],"fix":[],"checks":[],"protect":[]}`. The invalid answer is a check named with 65 `c` characters, which `Validate` refuses. Keep `cmd/kogen-setup`'s stdout JSON (`exit`, `configuration`, `error`) and its error line on stderr.

## Decisions
- On the Claude Code route, the init progress line reports the sum over the shaping rounds that ran (one or two), in the same `input=`/`cached=`/`output=`/`reasoning=` fields, taken from the usage that the executor round result reports. (source: request)
- When a round reports no usable usage, the line says `usage=unknown` in place of the four counters, and no zeros are printed. (source: request)
- The direct provider route and the `wall_ms` field are unchanged. (source: request)
- When the model never returns a valid configuration (`init_invalid`), the usage line is still printed to the progress stream before the error, on both routes, and the exit code stays 4. (source: request)

## Source comparison
- Addressed: "Claude route, one round reporting input 100, cached 40, output 10: the progress line contains `input=100 cached=40 output=10`". Scenario "One Claude Code round reports its usage" expects the whole line `kogen: init claude-sonnet-5-5/high input=100 cached=40 output=10 reasoning=0 wall_ms=<digits>`.
- Addressed: "first round invalid and a second valid, reporting 100/40/10 and 50/50/5: the line shows the sums `input=150 cached=90 output=15`". Scenario "A corrected Claude Code round adds its usage to the first" checks that 2 rounds ran.
- Addressed: "round reports no usage: the line contains `usage=unknown` and no `input=0`". Covered by scenario "A Claude Code round without usage reports usage=unknown" and by rule 2 for a two-round run where only one round lacks usage (scenario "One Claude Code round without usage makes the line unknown").
- Addressed: "Both rounds invalid on either route: stderr has the usage line, then the `init_invalid` error; exit code unchanged (4)". Covered by the two init_invalid scenarios, one per route. The error is the last stderr line, and the stdout JSON has exit 4 and configuration null.
- Addressed: "Direct provider route fixtures keep their current line byte for byte". Covered by scenario "The direct route's line is unchanged" (`kogen: init gpt-6.1-sol/high input=100 cached=0 output=20 reasoning=5`, the same counters as `TestInitWritesBridge...` at setup/init_test.go:801, which stays unchanged) and by scenario "The direct route still sums both attempts".
- Decided (technical): Claude Code reports no reasoning tokens (claudecode `mapUsage` leaves `Reasoning` nil). It counts as 0 in the `reasoning=` field, like the direct route's missing counts (`provider` `compatible`). "Usable usage" means `Input`, `Cached` and `Output` are all reported, which is the claudecode state `complete`. Partial usage is reported as unknown rather than as zeros.
- Decided (technical): the Claude route's `input=` value is the executor's `Usage.Input` as reported (input_tokens + cache reads + cache writes). The fixture therefore reports input_tokens 60, cache_read_input_tokens 40 and cache_creation_input_tokens 0 for "input 100, cached 40".
- Adjusted: "Using the existing scripted executor and scripted provider fixtures of the init tests". Intents may not use other Intents' step files, so the acceptance step carries its own copies of those fixtures: the scripted Claude Code runtime of `features/steps/provider-init.js`, extended to answer a resumed second round, and the Responses-API stream of `initSubmit`/`initUsage`. It runs them through the real `cmd/kogen-setup` entry point.
- Omitted: provider or executor failures other than `init_invalid` and interrupts keep printing no usage line. The request names only `init_invalid`.

## Tests
- The Claude Code route sums the usage of the rounds that ran, counts unreported reasoning as 0, and reports unknown when any round lacks Input, Cached or Output: a table-driven unit test, in a new or existing `setup` test file, of the function that combines the rounds' `executor.Usage` values into the printed counters. Cases: one complete round 100/40/10 → `input=100 cached=40 output=10 reasoning=0`; complete rounds 100/40/10 + 50/50/5 → `input=150 cached=90 output=15 reasoning=0`; one round with all fields nil → unknown; complete 100/40/10 + all-nil → unknown; a round with Input and Output but nil Cached → unknown. (unit)
- On the direct route, two invalid answers print the usage line with the sum of both attempts and still return provider/init_invalid with exit 4: extend `TestInitTwoInvalidAnswersEndWithNothingWritten` in setup/init_test.go to require that `f.err` contains `kogen: init gpt-6.1-sol/high input=200 cached=0 output=40 reasoning=10 wall_ms=` (two `initUsage` answers), keeping its existing assertions. (integration)
- The init progress line on the Claude Code route reports the round sums, or `usage=unknown`, and on both routes the line precedes the init_invalid error with exit 4: the acceptance scenarios in .kogen/intents/k-setup-init-claude-route-usage-reported/acceptance.feature, run through `cmd/kogen-setup` with the scripted Claude Code runtime and the scripted provider. (scenario)
- The direct route's successful line is unchanged: the existing assertion at setup/init_test.go:801 (`kogen: init gpt-6.1-sol/high input=100 cached=0 output=20 reasoning=5 wall_ms=`) passes without edits. (existing)
