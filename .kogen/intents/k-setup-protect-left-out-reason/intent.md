# Give dropped protect paths a reason in Left out

Slug: k-setup-protect-left-out-reason
Model: not applicable — this changes the text of one left-out entry derived from an existing eligibility check; no new state or rules
Acceptance:
- .kogen/intents/k-setup-protect-left-out-reason/acceptance.feature
- features/steps/k-setup-protect-left-out-reason__init.js

After verification, `kogen init` rechecks each proposed protect path against the checks that survived (`initResult.filterProtect` in `setup/init.go`, called from `initConfigure`). Today a path that no longer qualifies is appended to `res.leftOut` as the bare path, so the summary prints, for example, `Left out: lint (npm run lint) failed with status 2; package.json`: the reader cannot tell that `package.json` is a protect path or why it was dropped.

The product should instead append, for each protect path dropped by `filterProtect`, the entry `protect <path>: <reason>`, where `<reason>` is exactly the non-empty string that `initProtectProblem(p, text, ok, res.checks)` returned for that path in that same recheck (no prefix, suffix or rewording). For `package.json` without embedded verification settings this reason is `npm package and dependency metadata is editable; verification definitions or embedded settings can be protected as a whole`; for `mix.exs` it is `Mix project and dependency metadata is editable; verification definitions or embedded settings can be protected as a whole`. Entries keep their position: appended after the earlier left-out entries in proposal order, and the summary still joins all entries with `; ` on the one `Left out: ` line. Example (a failing `npm test` check `t` and a passing `u`, with the project's detected `test` check also failing):

```
Left out: test (npm run test) failed with status 1; t (npm test) failed with status 1; protect package.json: npm package and dependency metadata is editable; verification definitions or embedded settings can be protected as a whole
```

Boundaries: kept protect paths (the `Protect:` line and the committed `protect` list) are unchanged. Every other left-out entry is unchanged. When no check survived verification, `filterProtect` keeps today's behaviour: it does not recheck protection, keeps no protect path and adds no protect entry. Which paths are kept or dropped, validation, the committed `.kogen/project.yaml`, the other summary lines, stderr progress, the prompt and tool definition and exit codes do not change.

The acceptance step builds the `setup` test binary from a copy of the checkout with one extra driver test it writes itself (`TestProtectLeftOutReasonIntentCapture`), which uses the existing `setup` test fixture helpers `initNewFx`, `initSubmit`, `initScrub` and the `initFx` methods `program`, `write`, `commitAll`, `run` and `git`; keep those helpers and their signatures.

## Decisions
- A protect path dropped after verification is reported in the left-out list as `protect <path>: <reason>`, with the reason init's eligibility check computed for it. (source: request)
- Kept protect paths and every other left-out entry are unchanged; a run where all checks fail keeps today's behaviour and prints no protect entry. (source: request)

## Source comparison
- Addressed: Problem and Need (dropped protect path says it is a protect path and gives the computed reason, same style as other entries) in the prose and scenario "A protect path dropped after verification is reported with its reason".
- Addressed: synthetic example "tracked `package.json` with a real `test` script proposed for protection together with check `t` = `npm test`; `t` passes: path kept, no left-out entry" in scenario "Kept protect path has no left-out entry" (whole stdout, `Protect: package.json`, no `Left out:` line, committed protect `["package.json"]`).
- Conflicting, adjusted from observation: the request's second check `u` = `true` is refused by init's validation on the unchanged tree (`check u (true) runs nothing`), so the passing second check is `u` = `test -f package.json`. Its command does not appear in the requested output line.
- Conflicting, adjusted from observation: a root `package.json` with a real `test` script always makes init detect its own check `test` = `npm run test` (kogen-coordinator `project.Detect`). If that check passes, `package.json` stays eligible and nothing is dropped (scratch probe on the unchanged tree: `Checks: test, u`, `Protect: package.json`, `Left out: t (npm test) failed with status 1`). The fake `npm` therefore runs the same test script for `npm test` and `npm run test`, which share one exit status, so the requested line gains the detected entry at the front. The requested segments `t (npm test) failed with status 1; protect package.json: <reason>` are kept unchanged and in order as the end of the line: `Left out: test (npm run test) failed with status 1; t (npm test) failed with status 1; protect package.json: npm package and dependency metadata is editable; verification definitions or embedded settings can be protected as a whole`. On the unchanged tree this run prints `...; t (npm test) failed with status 1; package.json`.
- Addressed: "a repo whose checks all fail keeps today's behaviour (protect is not rechecked) and prints no protect entry" in scenario "All checks fail" (observed today: `Checks: none passed`, `Protect: none`, `Left out: test (npm run test) failed with status 1; t (npm test) failed with status 1`, plus the existing `Next:` line). This scenario passes on the unchanged tree and guards the preserved behaviour.
- Addressed: "existing init tests stay green" in Tests: the two existing tests that pin the old bare entry are updated to the new entry; all others pass unchanged.
- Omitted: no other output, configuration, validation or detection change was requested.

## Tests
- `filterProtect` appends `protect <path>: <reason>` for each dropped path, with the eligibility reason, and leaves kept paths and earlier entries unchanged: update `TestInitResultFiltersProtectionForKeptChecks` in setup/init_test.go so the "only ok" case expects left-out entries `protect package.json: npm package and dependency metadata is editable; verification definitions or embedded settings can be protected as a whole` and `protect mix.exs: Mix project and dependency metadata is editable; verification definitions or embedded settings can be protected as a whole` after `failed check`; the other cases are unchanged (unit)
- The summary of a run that drops a protect path prints the reasoned entry: update `TestInitLeftOutIncludesNewlyIneligibleProtection` in setup/init_output_test.go to expect `Left out: lint (npm run lint) failed with status 2; protect package.json: npm package and dependency metadata is editable; verification definitions or embedded settings can be protected as a whole` (integration)
- End-to-end through Init with a scripted provider and fake npm: kept path (no entry), dropped path (reasoned entry, committed protect empty), all checks failing (no protect entry): acceptance scenarios in .kogen/intents/k-setup-protect-left-out-reason/acceptance.feature (scenario)
- Kept protect paths and the other left-out entries are unchanged: the remaining existing init tests pass without edits (existing)
