# Report detected checks the configuration omits

Slug: committed-checks-omit-regression-suite
Model: not applicable — a read-only report comparing a committed check list with a deterministic detection has no meaningful state
Acceptance:
- .kogen/intents/committed-checks-omit-regression-suite/acceptance.feature
- features/steps/committed-checks-omit-regression-suite__notes.js

A project can bring its own Kogen configuration: committed earlier, written by hand or produced by an older version. When its checks leave out the project's test suite, `kogen init` accepts it silently today, so every later Build is green on the configured checks alone.

What the code does now (`setup/init.go`):
- Already-initialized path: `initRun` prints `Kogen is already initialized in <root>`, then the setup bootstrap Notes, then the cannot-fail check Notes, then `initNextLines(s, cfg)`.
- Leftover-commit path: `initCommitLeftover` commits the leftover configuration, prints `Initialized Kogen in <root>` and `Commit: <sha8> Add Kogen configuration`, then `initNextLines`. It prints no `Note:` lines at all.
- Detection: `initConfigure` lists the tracked paths with `git ls-tree -r -z --name-only HEAD`, reads each tracked path whose base name is in `initManifestNames` from HEAD into `manifests` (keyed by the full tracked path), and calls `project.Detect(manifests, tracked)`.

What the product should do after this change:
- Move the existing Note printing out of `initRun` into one shared function, for example `initAcceptedNotes(s, repo, cfg) error`. Both the already-initialized path and `initCommitLeftover` call it. It prints, with `s.Puts`, in this order:
  1. the existing `Note: setup command (<command>) looks like a one-time machine bootstrap` lines, unchanged;
  2. the existing `Note: check <name> (<command>) cannot fail: <runs nothing|masks its failure>` lines, unchanged;
  3. new: for each check in `project.Detect(manifests, tracked).Checks`, in detection order, whose `Run` is not among the configured checks' commands, one line:
     `Note: detected check <name> (<command>) is not in the configured checks`
     where `<name>` and `<command>` are the detected check's `Name` and `Run`, verbatim.
- A detected command counts as present when `initCommandKey(detected.Run) == initCommandKey(configured.Run)` for any configured check, whatever the configured check's name. A configured check with the detected name but a different command does not count as present. Detected checks that are present print nothing.
- Detection on both paths uses the same tracked paths and manifests that `initConfigure` uses: `git ls-tree -r -z --name-only HEAD`, plus the tracked paths whose base name is in `initManifestNames`, read from HEAD and keyed by their full path. Extract this collection into a helper that `initConfigure` also uses, so the inputs cannot drift. `initConfigure`'s own behavior and output do not change.
- On the leftover-commit path, the notes are computed after the commit, from the new HEAD (so a repository that had no commit before also works). They print after the `Commit:` line and before the `Next:` lines. On the already-initialized path they print after the `Kogen is already initialized` line and before the `Next:` lines. Running init again after a leftover commit prints byte-identical Note lines.
- Nothing is written, staged, committed, run or sent to a model because of these notes. No progress line is added. The configuration is not changed, migrated or re-detected into the file, nothing is refused, and the exit status is unchanged (0 on these paths). On the already-initialized path the working tree and HEAD are identical before and after. The leftover path still makes exactly its one existing commit.
- A configuration with only sound commands that covers every detected check prints no Note lines, and its output is identical to today's on both paths.

Replaced: the already-initialized branch's inline Note loops (moved into the shared function), and the leftover path's silence about notes. Unchanged: the first-run configure path, its `Replaced:`/`Dropped:`/`Left out:` lines, `project.Detect`, `initCommandKey`, the predicates and every `Next:` line.

## Decisions
- Line format, exactly: `Note: detected check <name> (<command>) is not in the configured checks`, with the detected check's name and command verbatim. (source: request)
- Comparison is by command after `initCommandKey` whitespace normalisation, under any configured check name. Extra spaces between words still match. A same-named check with a different command does not match. (source: request)
- One shared function prints all accepted-configuration notes on both paths, in this order: bootstrap setup Notes, cannot-fail check Notes, then detected-check Notes in `project.Detect` order. All of them come before the `Next:` lines. On the leftover path they come after the `Commit:` line. (source: request)
- Detection uses the committed tree (HEAD) with the same manifests and tracked paths as configuring. On the leftover path that is the HEAD the leftover commit just created. (source: request)
- Nothing is written, committed, run or sent to a model because of the notes. Exit status is unchanged. The configuration stays authoritative and unmodified. (source: request)

The request requires the same detection as configuring and the format `<name>` = detected name. So the Go acceptance expects `Note: detected check go-test (go test ./...) is not in the configured checks`, and the `vet`-only configuration also gets the `go-format` and `go-build` lines, which the request's "output contains" allows. A Go project detects four checks, so this example uses a project whose detection yields exactly one check named `test`: a `package.json` with script `test` (detected as `test` / `npm run test`).
